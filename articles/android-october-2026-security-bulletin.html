Android October 2026 Security Bulletin: 7 Critical Flaws, 25 CVEs

Google’s monthly AOSP patch closes 25 flaws — seven rated critical, 14 of them reachable without any user interaction. Here’s what the critical shortlist actually means, why Samsung ships extras, and what “2026-10-01” gets you.

Android WireShaman News Desk Oct 12, 2026 · 7 min read

Most Android security bulletins are a quiet monthly chore. October’s is not. Google’s October 2026 Android Security Bulletin — targeting the 2026-10-01 patch level on Android 16 through 17 — closes 25 vulnerabilities in the Android open-source project, and seven of them carry a Critical severity. Four of the seven sit in the system image itself, one lurks in the runtime, and one in the framework — and the majority need no user interaction at all.

The critical shortlist

Severity “Critical” in the Android bulletin means the flaw can escalate privileges or crash the system without the user doing anything, and without the code already holding special permissions. This month’s critical set, all with No in the “Additional permissions required” column and, for most, No in the user-interaction column:

  • CVE-2026-55269 — type confusion in art, the Android Runtime. A memory-corruption bug in the code interpreter that runs every app on the platform. Elevation of privilege, no user interaction.
  • CVE-2026-58835 — out-of-bounds write in system. OOB writes in the system image are the classic launchpad for chainable local exploits.
  • CVE-2026-55280 and CVE-2026-58880 — a pair of input-validation elevation bugs in framework. Both exploitable without user interaction.
  • Three Critical-rated denial-of-service flaws: CVE-2026-55271 in system, plus CVE-2026-49933 and CVE-2026-55336 in framework. Individually just a reboot; combined with the EoP set they give an attacker a reliable reset button.

In total, 14 of the 25 AOSP flaws can be triggered without any user action. That is the profile exploit developers hunt for: a reachable path on a device that is simply sitting there.

Why “no user interaction” is the line that matters

The bulletin’s interaction column is the field that tells you how far a flaw can travel. A vulnerability needing user interaction requires a click, a tap, or an opened attachment — which limits it to social-engineering-shaped attacks. A vulnerability with no user interaction can be fired at anything that reaches the attack surface passively: a network service, a message on a channel the device listens to, or local code an attacker has already planted.

Stack the pieces together — a runtime type-confusion EoP, an OOB write in system, framework input-validation EoPs, and DoS as a cleanup tool — and you have the raw material for a full local privilege-escalation chain that can run headless. Whether an in-the-wild chain exists is not yet public, but the components are all in the same patch.

Two flaws in the list deserve extra attention for device-specific reasons.

Four of the seven critical flaws escalate privileges with no user interaction and no special permissions. That is the shape of a local privilege-escalation chain.

Samsung ships critical extras and a permission-check fix

Samsung’s October bulletin adds two critical vendor flaws of its own: CVE-2026-21120, a use-after-free in vendor_wsmanager in the system image, and CVE-2026-21122, in the TTS library — both EoP, both on the 2026-10-01 Samsung patch level (October 8). Samsung also addresses a long-standing oversight in the framework’s Wi-Fi permission check: the isSystem parameter was never validated, so a non-system caller could pass true and inherit system-level Wi-Fi permissions. The October patch closes it on Android 17 — a reminder that the AOSP surface keeps changing underneath older OS levels.

What “single-part” means for your device

Google describes the October update as single-part: all listed AOSP fixes are delivered together rather than split into separate patch waves, and device makers are expected to ship everything in one release. So the practical question for any fleet is the same as every month — does your patch level read 2026-10-01? On Android 16, 16 QPR2, and 17, the criticals are closed only when the full single-part patch lands. OEMs ship on different clocks; an “October” patch on one brand may arrive weeks after another’s. For fleet operations, the patch level date, not the update name, is the control.

What this means for you

Verify the patch level, not the name. A device “updated in October” may still be missing the single-part AOSP fixes — check that it reports 2026-10-01 (or Samsung’s October 8 vendor level).

Assume local-escalation chains are buildable. If an attacker lands a foothold on a device — sideloaded app, compromised profile, network service — the critical EoP set in this bulletin gives them a headless path to system privileges until the patch lands.

Watch the Samsung track. The additional critical vendor flaws mean Samsung devices carry two more escalation paths that Android 17-only fixes (like the Wi-Fi permission-check miss) don’t close. Patch both tracks.

Pin your fleet to the 2026-10-01 level. On Android 16 through 17, the seven critical AOSP flaws are closed only when the full single-part update is present.
